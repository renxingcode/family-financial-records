# 协作风格与约定

> 本文档记录作者的编码风格、提交习惯、协作方式，作为后续开发的参考基准。
> 持续更新，每次发现新的偏好或约定时补充。
>
> **精简版见项目根目录 [AGENTS.md](../AGENTS.md)**（面向 AI 助手的快速上手指南，含目录结构/关键约定）；本文档是更详细的补充。

---

## 一、提交风格与节奏

### 1.1 提交节奏
- **作者自己提交**：AI 改完代码后不自动 commit，由作者 `git diff` 查看后自行提交
- **作者有自己的节奏**：可能一次合并多个改动提交，也可能分多次提交；一次只围绕一个主题，不批量堆砌
- **稳定后再合并**：特性分支上打磨稳定，作者自行 merge 回主干

### 1.2 Commit Message 风格
- **中文描述**，简洁明了，10-20 字概括本次改动
- **多改动点**：标题行（概括）+ 空行 + 正文（多条详细描述，条目之间无空行）
  ```
  导入导出与目标计算优化
  
  - 导入导出：JSON带目标数据、CSV补对比差额列
  - 目标计算：按年收入估算预计达成日期
  ```
- **简单小改动**（如 fix 小 bug）：一行即可，不必多行格式
- **字段名 / 专有名**：用 `<>` 包裹便于阅读（如 `<对比上次>`）
- **可混用 type 前缀**：如 `fix:`、`feat:`，但不强制；账单模块相关提交加"Bill"前缀
- **无关紧要的小改动**：可不写进 commit，避免啰嗦

### 1.3 Git 操作约定
- **不自动 push**：由作者自行推送到双 remote（origin=gitee，gh=github），命令 `git push && git push gh`

## 二、代码风格规范

### 2.1 注释规范
- **禁止装饰符**：html/ 内不要用 `=====`、`-----` 这类符号装饰注释标题；tests/ 里的 `----` 分隔保留
- **函数注释**：统一用 `/** */` 风格
- **无关紧要的注释词汇不要随意增减**：保持定稿稳定，不要这次加下次删
- **注释可以后期补充**：一开始没有的注释后边补上是正常的；一开始写错的注释后边改了也正常
- **但不要莫名其妙删大段注释**：比如参数说明，不要突然删掉后边某个版本又加回来
- **非必要不挪动代码**：纯粹移动位置、内容未变的（尤其 CSS），保持原貌

### 2.2 命名与文案
- **导出功能表述**：用"导出CSV表格/导出JSON"（动词在前），不用"CSV导出/JSON导出"
- **中文与英文/数字之间不加多余空格**：避免AI味，比如"避免AI味"不要写成"避免 AI 味"
- **代码变量名**：完整单词、驼峰命名、语义清晰（如 category1/category2，不缩写成 cat1/cat2）

### 2.3 数据安全优先
- **底层数据结构不能留 bug**：可能产生脏数据的问题（如银行卡重名、删除方式、目标金额写死）必须在当前版本解决，不能留到后续
- **页面样式类的"小尾巴"可以留作后续迭代**：但数据正确性问题不能拖
- **LocalStorage 存储 key 从一开始定死不变**：后续不能改

## 三、工作流程与协作方式

### 3.1 开发流程
- **先讨论方案再动手**：较大的改动先聊清楚思路，作者认可后再写代码
- **拿不准的问题主动问**：遇到多个可行方案或疑难问题，反向列给作者选择，不要一根筋自己钻牛角尖
- **一次一步**：改完一处、自测、交作者审核，再进行下一处，不批量
- **说明代码问题必须精准**：给出可验证的具体原因和场景，不夸大不误导

### 3.2 测试与验证
- **数据相关改动先跑测试**：工程化阶段后用 `tests/` 下的用例自测，并随功能演进持续补全覆盖场景
- **页面样式 / 视觉效果**：作者自己在浏览器、手机上人工验证
- **改完不改写作者的微调**：作者可能自行调整代码且不逐次告知，以工作区最新代码为准继续；若该差异阻碍开发再提出

### 3.3 文档维护
- **每次小版本定版后**：同步更新 CHANGELOG.md、README.md、AGENTS.md
- **主动检查文档更新**：不要等作者提醒
- **分清新增 / 优化 / 修复**：写 CHANGELOG 时以版本边界为准，不把上一版已有的内容重复计入

### 3.4 沟通风格
- **作者重视质量胜过速度**：不着急，慢慢打磨，宁可多花时间也要保证质量
- **作者会主动反馈问题**：发现 bug 会详细描述复现场景
- **作者喜欢被问问题**：拿不准就问，作者认可理由后自会采纳

## 四、项目管理习惯

### 4.1 仓库结构
- **html/**：持续开发的工作目录（account.html + assets/account.css + js/account.js）
- **html_single/**：单文件版（手动生成，用于手机 content:// 协议访问），含 mock 示例数据
- **docs/**：公开文档（ROADMAP、协作风格与约定）
- **tests/**：工程化阶段后的自动化测试（按模块分子目录）

### 4.2 版本管理
- **x.0 里程碑语义**：功能完整、稳定、可正式交付的宣告，不靠新功能数量；封版前功能冻结、打磨前置
- **V1.0 为账户模块稳定收尾版**，下一步 V1.1 工程化拆分，为引入账单模块打基础

### 4.3 双仓库发布
- **gitee**（origin）+ **github**（gh）双 remote
- 推送命令：`git push && git push gh`
- 协议：Apache 2.0 + NOTICE

## 五、AI 协作注意事项（自我提醒）

1. **不要偷改历史代码**：之前写好的注释、样式，不要莫名其妙删掉或改回
2. **不要自动 commit**：改完代码放着，告诉作者 commit 内容，作者自己提交
3. **不要自动 push**：由作者操作
4. **每次改完输出 commit 备注**：纯文本、简短描述，不写 `git commit -m`，方便直接粘贴
5. **涉及数据的改动必须先自测**：跑测试用例，并思考覆盖是否完整
6. **主动检查文档是否需要更新**：不要等作者提醒
7. **临时文件集中管理**：统一放临时子目录、用完即删，不零散堆放、不进版本库
